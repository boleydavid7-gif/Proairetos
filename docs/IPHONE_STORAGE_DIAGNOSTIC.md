# iPhone storage diagnostic

Status: built and checked in Chromium. **Not yet run on an iPhone.** No iPhone result exists in this document,
because none has been measured; the owner runs it on their device and sends the copied results. Nothing here assumes
what they will say.

## Why

Proairetos reads other apps' records from browser storage (`storedRecords.ts`), tells them about changes over a
BroadcastChannel, and relies on one service worker at `/` for notices. All of that works when the apps share one
browser storage. An iPhone Home Screen app may have storage of its own. Until measured, no design may depend on
shared storage between separately installed apps.

## What it is

Temporary pages, one per app, under `/lab/diag/<app>/` for Hydros, Soma and Meletē (`public/lab/diag/`, generated by
`npm run apps:build` from the manifest, `src/core/apps/diag.ts`). The path sits outside every app's own scope, so no
app's service worker or cache ever sees it, and the main worker already leaves `/lab/` alone. Each page has its own web
manifest (scope and start address are its own folder), so each can be added to the Home Screen as a separate install.
The pages are `noindex`, not in the sitemap, and load one script and one style sheet from the site (no inline script).

It does **not** touch the apps, their storage, sign-in, sync, the Worker or the database. It makes no network request.
Everything it writes starts with `proairetosDiag` or `proairetos-diag`, and cleanup removes only those.

What each page writes (a "mark": app, a random install id kept in localStorage, the time, whether standalone):
localStorage key, an IndexedDB database with one record, a Cache Storage cache with one entry, a cookie, a
BroadcastChannel message, and a registered worker for its own folder. What it reads: every mark of all three apps that
this install can see in each place, the list of registered workers and cache names it can see, display mode (the
`display-mode` queries and `navigator.standalone`), the storage estimate (`usage`, `quota`) and `persisted`.
Buttons: Write marks, Read, Copy results (JSON), Save file, Remove marks.

## How the owner runs it

Use the built site (after this branch is deployed, or a preview build).

1. In Safari open `/lab/diag/hydros/`, then Share, Add to Home Screen. Repeat for `/lab/diag/soma/` and
   `/lab/diag/melete/`. Leave one Safari tab open on `/lab/diag/hydros/`.
2. Open each of the three Home Screen icons in turn and tap **Write marks**.
3. Open each icon again and the Safari tab, tap **Read**, and read the table: which apps' marks each place shows.
4. For the BroadcastChannel row, keep one icon in the app switcher, open another, tap **Write marks**, then go back to
   the first and tap **Read**. "Broadcast heard" lists the other installs that spoke while both were alive; nothing
   there is inconclusive if iOS suspended the other app, not a no.
5. In each place tap **Copy results** and paste them to Claude (four results: three icons and Safari).
6. Tap **Remove marks** in every place, then delete the three Home Screen icons.

Reading the table: `(this install)` is the place's own mark; a mark from another app with a different install id in
brackets means that storage is shared with that other place.

## Checked so far (Chromium, not an iPhone)

`scripts/diag/selftest.mjs` proves the tool works, not what iOS does:

| Check | Result |
| --- | --- |
| Three pages in one browser context see all three marks in localStorage, IndexedDB, Cache Storage and cookies | passes |
| BroadcastChannel carries the other pages' messages | passes |
| Each diagnostic worker is listed | passes |
| Display mode and the storage estimate are read | passes |
| Three separate contexts each see only their own marks | passes |
| Cleanup removes every mark, cache, cookie and worker it made, and leaves other keys alone | passes |

WebKit itself was not run here (no WebKit build in this environment).

## What each outcome would mean

Fill the table from the four results.

| Mechanism | Safari sees Hydros / Soma / Meletē marks | Each icon sees the others' marks |
| --- | --- | --- |
| localStorage | | |
| IndexedDB | | |
| Cache Storage | | |
| Cookies | | |
| BroadcastChannel | | |
| Service workers listed | | |

- **A. Every install is isolated, and Safari too.** Separately installed apps cannot read each other's records, hear
  each other or share a worker. Today, search and notices in Proairetos cannot see an app that lives in another
  install, so the shared layer has to be the account's sealed sync: each install syncs its own records, and
  Proairetos reads an on-device copy of the others' search projections after sync (see `PROVIDER_CONTRACT.md`). Cross-app
  live updates (the family BroadcastChannel) work only inside one install.
- **B. Installs share nothing with each other but Safari shares with them** (or the reverse). The shared layer still
  has to be sync for installed apps; Safari-only use keeps working as today. Documented rules must not assume which
  place the person uses.
- **C. All places share storage.** The present design works as written. Sync stays the backup, not the bridge. Even
  then, no design should depend on it without a per-device check, since it can change between iOS versions.

In every outcome the diagnostic's rule stands: no production feature depends on shared storage between installs.
